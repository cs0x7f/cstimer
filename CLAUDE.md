# CLAUDE.md

<!-- Owned by Agentic OS (agentic-os-template). Updated by `copier update`.
     Do not edit this file in the project; project rules go in CLAUDE.project.md. -->

Behavioral guidelines to reduce common LLM coding mistakes, followed by the
conventions every Agentic OS project shares. Project-specific rules are in
`CLAUDE.project.md`, imported at the end.

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

## 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

## 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

## 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

## 5. Agentic OS Conventions

### Ownership
- Framework files (this file, `.claude/settings.json`, `.claude/loop.md`,
  `.claude/agents/`, `.claude/skills/` shipped by the template, `agentic-os/`,
  `.github/workflows/`, `.gitignore`) are owned by the template and
  replaced on `copier update`. Do not edit them in the project; propose the
  change for the template instead: add a line under "Agentic OS" in
  BACKLOG.md saying which file, what should change, and why. The edit hook
  warns when you touch one of these files; the maintenance loop reports the
  open proposals.
- Project files (`src/`, `tests/`, `plans/` incl. `plans/SECURITY.md`, `BACKLOG.md`, `README.md`,
  `CLAUDE.project.md`, `.claude/loop.project.md`, Dockerfile and compose
  files, `.env*`) are owned by the project. The template never touches them
  after the first render.
- `agentic-os/README.md` explains the framework and how to update it.

### Language
- Code, comments, commit messages and repo docs are English.
- Conversation with the owner is Norwegian.

### Planning and memory
- Plans and design docs live in `plans/` in the project root, never in
  `~/.claude/plans/`. After writing a plan, summarize it in chat before
  implementing.
- `BACKLOG.md` in the root is the single list of open and done work. When a
  backlog item ships, tick it and add the date and the plan file.
- Handoffs between sessions, machines or tools are written as
  `plans/<topic>-handoff.md` using `agentic-os/templates/handoff.md`. A
  handoff states what is done, what is verified, what is untested, and what
  the receiver must decide.

### Git
- The owner runs every `git commit` and `git push` themselves. Leave changes
  in the working tree and say which files are ready and a suggested commit
  message. Never commit or push, even to fix a forgotten file.
- Work on a branch or in a worktree when the change is large or when a loop
  is running in parallel.

### Verification
- Container projects: there is no Docker on the dev machine. Images are
  built and verified by CI (GitHub Actions to GHCR) and run on the UMDS home
  server via `compose.server.yml`. Verify locally with tests and lint, not
  with `docker build`.
- Non-container projects (desktop apps, watch apps, libraries): the build
  and the test run are local; `CLAUDE.project.md` says how. CI only scans.
- A `PostToolUse` hook (`agentic-os/edit_hook.py`) reminds you that a source
  change needs a mirrored test, and warns when you edit a template-owned
  file. Act on both before calling a task done.
- The `/verify` skill, when the project defines one, is how a change is
  checked by observation. Prefer it over "the tests pass" for UI and I/O.

### Design (Marker)
- Projects with a UI use Marker, the shared design system, shipped in
  `agentic-os/marker/` (template-owned): `tokens.json` is the source,
  `tokens.css` the file the app loads, `MARKER.md` the decisions and the
  patterns. Read `MARKER.md` before writing any CSS or markup.
- Every colour, spacing, radius, control height and type style is
  `var(--token)` from `tokens.css`. Never a hard-coded colour; the sizes
  `MARKER.md` names literally (hairline, stripe, scrim, transition) are the
  exceptions.
- One filled button per view: `--primary` / `--primary-ink`. No other button
  has a fill.
- `--accent` (orange in the template) is a detail: mark, marker stripe, icon.
  Never button fill, focus border or selected row. The accent trio
  (`--accent`, `--accent2`, `--accent-bg`) is the only thing a project
  rebinds, in the project's own stylesheet after `tokens.css`.
- All numbers and all status text in `--font-mono`, signs written out
  (`+82.40`, `−31.10`). Status is always dot + word, never colour alone.
- Font weight is 400 or 500. Never 600 or 700.
- Focus is `:focus-visible` with the `--focus` outline (already in
  `tokens.css`), not `border-color`.
- Elevation: a card is `--bg2` + `--shadow-card`; `--shadow` only on what
  floats above the page (modal, popover, toast).
- Dark is the default theme; `data-theme` on `<html>` switches. Both themes
  must be checked before a UI change is called done.

### Security
- `agentic-os/SECURITY-CHECKLIST.md` is the master list; `plans/SECURITY.md`
  is this project's status against it. Before a change that touches routes,
  auth, sessions, uploads, file writes, secrets or exposure is called done:
  walk through the relevant sections, run `/security-review`, and update
  `plans/SECURITY.md`.
- A new route is private by default. Public routes are listed in
  `plans/SECURITY.md` with a reason.
- Traffic is HTTPS, also on the LAN. A plain-HTTP port is a documented
  deviation in `plans/SECURITY.md`, never an unstated default.
- First public exposure and every auth change afterwards: the whole list,
  plus the ZAP baseline scan (section 6).

### Loops and unattended work
- A loop never grades its own work. Verification is done by the `checker`
  subagent (`.claude/agents/checker.md`) with fresh context, not by the
  session that made the change.
- Loops that change code work in their own git worktree
  (`isolation: worktree`) so they do not collide with the owner's tree.
- Every loop has an explicit stop criterion and a maximum number of
  iterations. No loop runs forever without a human checkpoint.
- Loops against live systems (UMDS services, broker accounts) are
  read-and-report only. Acting requires a human.
- Loop definitions are skills under `.claude/skills/`; loop state between
  runs is written to `plans/loops/PROGRESS.md` (project-owned).
- A session that runs loops unattended starts with the stricter permission
  set: `claude --settings .claude/settings.loop.json`.
